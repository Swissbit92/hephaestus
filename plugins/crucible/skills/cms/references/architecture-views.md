# Architecture views — schema and authoring rules

Loaded only when rendering. `SKILL.md` carries the two-line summary; everything
that would bloat it lives here.

## The contract

`docs/ARCHITECTURE.md` is the source. `docs/ARCHITECTURE.html` is generated by
`scripts/render.py` and **must never be hand-edited** — the moment someone edits
the output, the single-source claim collapses and you are back to two documents
that disagree.

Diagram models live in fenced ` ```archview ` blocks *inside* the markdown, so
there is one file to edit and one linter to satisfy. Prose between the blocks is
what does the teaching; a diagram with no sentence explaining which question it
answers is the artifact people look at and do not understand.

## `archview` schema

```json
{
  "caption": "one line under the figure — say what question it answers",
  "nodes": [
    {
      "id": "unique",
      "label": "what it is called",
      "sub": "what it does — optional second line",
      "tech": "what it is built from — optional third line",
      "kind": "module | service | store | external | secret",
      "group": "GROUP_ID"
    }
  ],
  "edges": [
    {"from": "a", "to": "b", "label": "optional", "style": "flow | static"}
  ],
  "groups": [
    {"id": "GROUP_ID", "label": "boundary label", "members": ["a", "b"]}
  ]
}
```

**Node order matters.** Layering is longest-path over edges whose target appears
*later* in the node list; an edge pointing backwards becomes a back edge and is
drawn as a margin rail. So list nodes roughly in flow order and the layout
follows your intent.

**`kind` is semantic, not decorative:**

| kind | use for | rendered as |
|---|---|---|
| `module` | code you own inside this repo | plain box |
| `service` | a process/entry point | accent border |
| `store` | a database, table, queue, bucket | green border |
| `external` | anything you do not control | dashed border |
| `secret` | a credential store | red border |

**`tech` is C4's convention**, not an extra view. Technology annotates the
container it belongs to; a separate "tech stack" section goes stale on its own
schedule and nobody reads it twice. Put it on the nodes and it is visible in
every diagram that shows them. Omit it on process-flow diagrams — steps are not
containers.

**`style: "static"`** draws the connector without motion. Use it for
relationships that are structural rather than active — "M2 only", "supervises".

## Groups

A group box is the bounding box of its members plus padding. Two rules keep it
clean, and `check_arch.py` C4 enforces the second:

1. Members should sit on the same row, or on consecutive rows.
2. A node that is *not* a member must not fall inside the box. If the layout puts
   one there, the group is spanning rows it does not own — split it, or move the
   stray node into it.

## `archflow` schema

A topology answers "what is here". It cannot answer "what happens when a request
arrives", and the usual workaround — a second diagram of the same boxes with
different arrows — puts the same facts in two places and lets them disagree.

An `archflow` block instead *walks* an existing `archview`. Same boxes, same
layout, no second copy: selecting a flow dims everything not on its path, and
prev/next steps through it one hop at a time.

```json
{
  "view": "topology",
  "flows": [
    {
      "id": "read-path",
      "label": "Serving a cached read",
      "steps": [
        {"node": "client",  "note": "one sentence — what happens at this step"},
        {"edge": ["client", "gateway"]},
        {"node": "cache",   "note": "hit, so the store is never touched"}
      ]
    }
  ]
}
```

- **`view`** names an `archview` on the same page. Give that block an `"id"`;
  without one it is addressable positionally as `f1`, `f2` … in document order.
- **A step is exactly one of `node` or `edge`.** An edge is the `[from, to]` pair
  as written in the view — not a separate identifier.
- **`note`** is the caption shown while that step is current. Optional; the flow
  label is used when it is absent. Write it as a sentence, not a fragment: it is
  read aloud by a screen reader as the step changes.

**Order matters.** An `archflow` must appear *below* the `archview` it walks.
Resolution is a single forward pass, so a flow declared first cannot see its view
and the render fails rather than emitting a picker that highlights nothing.

Every reference is checked when the page is built. A step pointing at a node or
edge that is not in the view, a duplicate flow id, or an unresolvable `view` all
stop the render and name the offending id alongside the valid ones. This is
deliberately a build error and not a `check_arch.py` code: that checker only ever
reads the emitted SVG, where a dangling reference is invisible — a broken picker
and a working one produce identical geometry.

Flows are deep-linkable: selecting one rewrites the fragment to
`#flow=<id>&step=<n>`, and opening that link restores it.

## The mechanism socket

Fenced ` ```html ` blocks pass through untouched. This is the deliberate escape
hatch: every repo does one characteristic thing, and that thing cannot be
expressed in a generic node/edge schema. A trading service draws its order book,
a data pipeline draws its window, a web app draws its request path.

Inline anything you need — SVG, a `<script>`, CSS using the page's custom
properties (`var(--accent)`, `var(--faint)`). Keep it self-contained; the page
opens from `file://` with no network.

## Which views to write

Every view must answer a **different question**. A view without its own question
is decoration, and decoration is what rots first.

| Question | View | When |
|---|---|---|
| What is this repo, what does it touch? | topology | always |
| What does it own — the blast radius? | data/resources | when it owns shared state |
| What holds credentials, what can act? | trust boundary | when it holds any |
| What happens when it runs? | `archflow` over the topology | when non-obvious |
| What is the mechanism? | `html` socket | repo-specific |
| What will bite me? | **prose, not a diagram** | always |

Resist adding a view that restates something already in `ROADMAP.md`,
`LESSONS_LEARNED.md` or an ADR. Duplicated truth is the first thing to drift.

## Frontmatter

Standard CMS fields, plus three optional ones the renderer reads:

- `accent: "#RRGGBB"` — the page's accent colour. Visual identity belongs to the
  repo, not to this skill.
- `stage: word word` — short chips in the page header.
- `published_url: https://…` — where the rendered copy is published. The page
  renders it as a CANONICAL COPY link in its own footer, so a copy that has been
  mailed on or re-hosted still says where the live one lives, and `render --publish`
  redeploys to that same address instead of minting a new one each time.

## Publishing

`render.py --publish` does not publish. It renders, then prints one manifest line:

```
PUBLISH  docs/ARCHITECTURE.html  url=https://…  title="repo — Architecture"
```

The agent reads that line and performs the upload. The split is not ceremony —
this renderer is pure stdlib with no network and no credentials, and it stays
that way. A doc with no `published_url` yet prints `PUBLISH-NEW`; publish it,
then write the returned address into the frontmatter so every later render
targets the same link rather than scattering copies.

## Staleness

`render.py --check` compares **content hashes**, not mtimes:

- hash of the source markdown — edit it and the page is stale
- hash of `render.py` itself — change the renderer and every page it produced is
  stale while its source is untouched

git does not preserve mtimes, so an mtime comparison reports a byte-identical
page as stale after any checkout or merge. `check.py` surfaces staleness as a
**Warning**, never an Error — a gate that blocks on a regenerable artifact is one
people learn to bypass, after which it protects nothing.

## Structural check

`scripts/check_arch.py <page.html>` parses the **emitted SVG** (not the layout
engine's intermediate geometry — the artifact is what ships) and reports:

| code | violation |
|---|---|
| C1 | node rects overlap |
| C2 | a connector passes through a node's interior |
| C3 | geometry outside the viewBox |
| C4 | a group box does not contain its members with padding |
| C5 | degenerate geometry (zero/negative dimensions) |
| C6 | a malformed or empty connector path |

A page with **no diagrams is not a failure** — most repos have prose long before
their first `archview` block, and flagging them would make the check cry wolf.

Run it after any change to the layout engine. It has already caught two real
routing bugs in a page that had been committed, pushed and called finished:
a multi-row edge dropping straight through an intervening node, and a back-edge
rail returning horizontally through whatever sat between the lane and its target.
Neither was visible without measuring.
