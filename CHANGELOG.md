## [Unreleased]

### Added

- **crucible 1.8.0: the changelog is cut at release, and old history is archived instead of piling up.** `CHANGELOG.md` had held every release since 0.6.3 under one `[Unreleased]` heading (115 KB; nothing in the release flow ever moved it, and the `cms` checks skip the file). New `scripts/changelog.py`: `cut` moves `[Unreleased]` under `## [<plugin>-v<x.y.z>] — date` and refuses an empty section or a duplicate heading; `check` tests for the heading; `archive` and `archive-lessons` move old entries to `docs/archive/YYYY-MM/` (dry run unless `--apply`; ages come from the date in the entry's own heading, never mtime); `report` prints sizes, `ARCHIVE DUE` and name-based removal candidates, and never changes or deletes anything. `scripts/release.sh` checks the heading before the gates (auto-cuts when it will make the release commit, refuses when it will not, since `main` is protected), and every dry or real run ends with the report. The `cms` check gains `check_doc_budgets`: a stateless warning when `CHANGELOG.md` passes 40 KB or `docs/LESSONS_LEARNED.md` passes 25 KB, measured in bytes because 87 KB in 120 lines was invisible to the line-count trend check. One-time cleanup: the 95 entries in `[Unreleased]` were regrouped under the tag that first shipped each one (by `git blame`, since 68 of 104 bullets carried no version label) and everything older than the newest 5 versions moved to `docs/archive/2026-10/CHANGELOG.md`; `CHANGELOG.md` went from 119,320 to about 20 KB with all 104 bullets kept. ADR convention written down: `Superseded by ADR-NNN`, `Accepted (amended by ADR-NNN)`; the ADR template gains the amended form. `develop.md` Phase 6 points at the release report. Removal PRs state a reason per deleted test.

## [crucible-v1.7.1] — 2026-10-25

### Added

- **Evals: two-turn runs and older releases.** A scenario can carry a `followup` (resumed in the same session; its tool calls are turn 2), `tool_called_in_turn` and `assistant_text_matching` assert on a given turn or any message, `disallowed_tools` removes a tool the scenario must work without, and `run_evals.py --plugin-root NAME=DIR` runs an older release under the same harness so a baseline and a candidate differ only in the plugin. Three `task-list-*` scenarios.

### Fixed

- **crucible 1.7.1: `/crucible:develop` shows its task list again, with an estimate per phase and a total.** The list had gone missing for two reasons. The task tools (`TaskCreate`, `TaskUpdate`) are off by default in current Claude Code and come back with `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` in the `env` block of settings.json. And "create a task list" was one clause inside the Phase 0 paragraph, which both 1.6.1 and 1.7.0 skipped (0/5 on Sonnet 5.5, 0/5 on Opus 5.5; 1.7.0 also dropped "keep it current"). develop now opens with a **FIRST** step: `TaskCreate` is the first tool call, each title ends with an estimate, the first carries the total (`Phase 0: Classify & align (~5 min) — total ~90 min`), tasks go in_progress and completed at each gate, and the estimates are revised when a milestone overruns. With no task tool, the same list is printed as a checklist rather than skipped. Measured on the same scenarios: list at turn 1 **0/5 → 5/5** (Sonnet), 0/5 → 4/5 (Opus); kept current after the user confirms 0/3 → 6/6; plain-text fallback 0/5 (1.6.1) and 1/5 (1.7.0) → 5/5; the 8 existing develop scenarios unchanged.

## [crucible-v1.7.0] — 2026-10-24

### Added

- **crucible 1.7.0: `qa_gates.py` runs Phase 4.0 once, in one call.** It runs every deterministic gate for the repo: what `detect_profile` emits, the revert probe (plus `--mutate` with `--final`) and the invariants. Read-only gates run concurrently. Test-executing gates stay serial unless `.crucible/qa.json` declares the suite parallel-safe, because a suite with a fixed port goes flaky under concurrency, and a flaky REJECT spends a fix round. The output is one line per gate, the tail of each failing one, and `QA-GATES: PASS|FAIL|UNDETERMINED|SKIP`. The verdict is stored per tree content, and the gatekeeper reads it (`--show`) instead of re-running the suite. A gate that crashes counts as could-not-determine, never as a finding. Measured on a counting fixture: a QA round went from 7 test collections and 5 pytest sessions (2 full suites) to 2 collections and 4 sessions (1 full suite), and to 1 collection once the branch-point cache is warm.

- **The branch point is cached.** `coverage_delta` and `metric_delta --metric ruff` cache their base-side result in the git common directory. The key is the base sha, the command, the interpreter and the script's own content. Only successful results are stored, and `--no-cache` or `CRUCIBLE_NO_CACHE=1` bypasses it.

- **Leaner instructions.** `develop.md` went from 18,531 to 12,053 bytes, and `qa-gatekeeper.md` from 13,336 to 6,998. Every check was kept; the explanations moved one link away, into `commands/references/develop-rationale.md`. Subagents are asked for capped reports: research about 600 words, the plan about 1,200, the gatekeeper about 400, findings only.

- **`finish-branch` recommends a PR when the target runs CI.** `integrate.py recommend` reads the *target's* tree, since a branch that adds a workflow proves nothing about the branch it merges into. It also checks protection where possible. finish-branch leads with Open PR and says why, and still never chooses. With no remote, a PR isn't possible, and it says so.

- **A declared promote step.** `integrate.py promote` prints the repo's declared release path from `.crucible/release.json` (from, to, via, command, dry run) and runs only the dry run. It detects and reports release-please, changesets and semantic-release. The release command itself is never run by the script: it needs the user's explicit go for that exact action (act-for-real). This repo declares dev → main via PR → `release.sh`.

- **ULTRA, an opt-in tier for long runs.** It is FULL plus long-run controls, and it is never auto-classified: the ledger refuses `--tier ULTRA` unless the user's own words say so. The user sets checkpoints at plan approval; a milestone that passes at one returns `STOP CHECKPOINT-PREREGISTERED`, and nothing else starts until the user clears it. Between checkpoints the run carries on without asking and logs each choice it made alone (`decide`). With `--criteria`, the acceptance criteria are frozen: PASS and ship refuse if anything other than a `pass` flag changed. Research may fan out to read-only agents; writing stays single-threaded.

- **Evals measure cost.** Each run records duration, tokens, cost, turns and subagents (`None` rather than 0 when a timeout drops the data), and reports carry per-scenario medians. New scenarios cover ULTRA checkpoints (stop and proceed) and PR-when-CI (with a no-CI control). There's a new `file_not_matching` check. The two Phase 4 scenarios now grade the gates' own output rather than the script names.

### Fixed

- **crucible 1.7.0: `qa_gates` resolves an interpreter that can actually run pytest.** On a machine whose `python3` has no pytest (the Homebrew default), the tests gate reported "No module named pytest" as exit 1, which read as *failing tests* when nothing had been tested. It's the same missing-tool-as-failure defect fixed in 1.6.1, at a new site. The runner now resolves the repo's own `.venv`/`venv`, then the running interpreter, then `uv run --with pytest`, and uses that for the suite, the coverage collector and the mutation probe. With none of them available, it reports *could not determine* (exit 2). The final evaluation found this: agents trusted the one-call verdict and stopped. The milestone ledger also no longer treats a pass as permanent: a REJECT after a PASS reopens the milestone, so a regression found in final verification counts against the budget.

- **crucible 1.7.0: two gaps found by the final evaluation, fixed before release.** First, `qa_gates.py` ran only what `detect_profile` emitted, and the detector skips a repo with bare pytest-style tests and no manifest. In 1.6, develop had covered that case with an explicit coverage step that the runner replaced. So for such repos neither the suite nor the coverage delta ran (`develop/phase4-runs-the-coverage-check` went 3/3 → 0/3). The runner now adds both when pytest-style tests exist and no test gate was emitted. Second, `mutation_probe --revert` treated bytecode left by an earlier gate's test run as changed source files. It now ignores generated caches, like `qa_gates`' tree key already did.

- **crucible 1.7.0: a timed-out command could leave its children running without bound, which froze a 48 GB Mac.** `subprocess.run(timeout=)` kills only the direct child: `uv`, `sh` or `claude`. The real worker, a pytest grandchild, keeps running as an orphan. During a 24-wide eval run, `mutation_probe --mutate` planted a mutant that looped forever appending to a list. Two orphaned test runners grew to about 100 GB each until the system killed processes, and the user had to kill Terminal. Every place that runs a project's code now goes through `crucible_common.run_bounded`: `mutation_probe`, `qa_gates`, `invariants_run`, the `integrate` dry run, the eval runner, `coverage_delta` via `run()`, and `loop_sweep`. `loop_sweep` gets its own copy, because a skill must work without the plugin's scripts, and it previously had **no timeout at all**. Each command gets its own session or process group. On timeout, the group and every descendant are sent SIGTERM, then SIGKILL after 2 s, and reaped (on Windows, `taskkill /T /F`). After a normal exit, anything left in its group is killed. A **memory watchdog** caps the tree's resident memory at min(8 GB, a quarter of RAM): 4 GB on a 16 GB laptop. It's a watchdog because macOS doesn't enforce `RLIMIT_AS`. `CRUCIBLE_MEM_LIMIT_MB` overrides it. `run_evals` also bounds the whole suite: all concurrent runs together get at most a quarter of RAM, at 2 GB or more each, so `--jobs 24` becomes 6 on 48 GB and 2 on 16 GB, with a printed note. The regression tests (`tests/test_bounded_run.py`) cap themselves, so a regressed fix fails a test instead of filling the machine: the first delete-the-fix check, before they did, grew a runaway to 32 GB. `mutation_probe` also gained `+=`/`-=` mutations, which it had skipped.

- **crucible 1.7.0: the clone gate crashed on a long pasted line** (shipped in 1.6.0). Two token windows on one line share their first and last line. The region sort then compared dicts, raised `TypeError` and exited 1, which read as "new duplicated code". Running `qa_gates.py` on its own branch exposed it. `release.sh`'s dev fast-forward read a git-config key nothing ever writes and returned `dev` on both branches of its conditional; it now reads `from` in `.crucible/release.json`. Its `--dry-run` may now preview from a branch other than `main`.

## [crucible-v1.6.1] — 2026-10-24

### Fixed

- **crucible 1.6.1: a missing tool was reported as an INVARIANT VIOLATED.** `invariants_run` treated a check's own exit 2 as a failure unless the message began with one of two internal phrases. The pytest-based checks also exited 1 when pytest was missing, which is `python -m pytest`'s code for failing tests. On a machine without pytest, two invariants read as broken when neither had been checked. Any exit 2 from a check is now *undetermined*, and `scripts/checks/_python.sh` gained `run_pytest`, which maps a missing pytest and pytest's own codes 2–5 (interrupted, internal error, usage error, nothing collected) to 2. The same defect lived in `release.sh`, which said "test suite is red" when pytest wasn't installed; it now says pytest is missing. Fixed at all three sites. `mutation_probe --revert` confirmed the new tests fail without the fix. `docs/ARCHITECTURE.html` is re-rendered; it had been out of date with its source.

## [crucible-v1.6.0] — 2026-10-24

### Added

- **crucible 1.6.0: `develop` milestones have a fix budget.** The QA loop was "REJECT → fix, re-run QA; do not proceed until PASS", with no cap. `milestone_ledger.py` replaces it. Each milestone gets 3 fix rounds, and every REJECT counts whatever its cause. A milestone in a peer project ran about 7 rounds because each failure had a different cause, so a cap that only counts repeats of the same failure never fired. Environment failures get a separate setup budget, and there's a time cap at twice the estimate. When the same gate fails twice, develop stops to find the cause before trying again. At a cap develop stops and asks you: **ship** the best result, **continue**, or **restart** from the plan. Only your recorded words (`--user-said`) change a budget. FULL milestones open with their own narrow research, run alongside the build, and a PASS cannot close a FULL milestone without it. The ledger lives in the git directory, one file per branch, and is never committed. New evals: `develop/stops-at-the-fix-cap` and `develop/full-milestone-records-its-research`.

- **Delta gates: `metric_delta.py`.** Duplicated code and ruff findings are compared as *sets of findings* at the current merge-base, not as counts. Findings that already existed never fail a branch (one peer repo had 2,122 at its branch point). Fixing one finding and adding another can't hide behind an unchanged count. Clone detection is language-agnostic and exact-copy only in v1. `detect_profile` emits the clones gate once per repo and runs ruff lint as a delta. New eval: `develop/phase4-runs-the-delta-gates`.

- **`mutation_probe.py`, in a throwaway copy, never your tree.** `--revert` restores the branch point's code and re-runs the changed tests, which must fail; it runs every milestone. `--mutate` plants up to 6 defects in the changed functions and lists the ones the tests miss; it runs at the final milestone. Two canaries run first: the copy's tests pass, and a sentinel import error is caught. Without the second, a suite that imports some other copy of the code (an editable install, say) would pass every probe by accident.

- **`qa-gatekeeper` §4e, every occurrence:** a fix covers every instance of the defect, with the worst case shown, and each new code clone needs a stated reason. §4b also gains the revert result and a rule that input fixtures are checked against a real data sample.

- **`develop`: smaller additions.** The coordinator re-checks agents' reports before passing them on, and teams default to at most 5 agents. The planning brief asks why new code couldn't reuse existing code. Changes to anything a model produces go to `eval-first` at Phase 2.

- **`eval-first` pre-flight** (`references/statistics.md`; `reliability.py ci|n`): run one case twice (identical outputs mean repeats measure nothing), then check the Wilson interval and the number of cases needed for the smallest change worth detecting.

- **Eval baselines record their conditions.** A `meta` block holds model, CLI version, k, plugin revision and develop fix cap. Comparing against a baseline taken at a different k or with a different model exits 2. `--scenario` can be repeated, and `--jobs N` runs repetitions and scenarios concurrently without changing k. A new `file_matching` check grades a file's end state (it can reach into `.git/`) rather than the spelling of a command, and a `bash_matching` miss now prints the commands it did see. Both came out of this release's own measurement: a correct run that called the ledger through a shell variable was scored as a miss.

### Fixed

- **crucible: the emitted coverage gate exited 2 on every Python project.** `detect_profile --emit-gates` printed `python3 "$CRUCIBLE_SCRIPTS/coverage_delta.py"`, and nothing ever set that variable. Python was asked to open `/coverage_delta.py`, and develop counts any non-zero exit as a QA failure, so Phase 4.0 failed for every Python project. Nested roots also doubled their path (`cd <root> && … --repo <root>`). Gate lines now carry the absolute script path and `--repo .`. A test runs an emitted line through a shell, because this defect only showed up when the line was executed, never when it was read. The gate scripts also share `crucible_common.py`, which reads the integration target `start-branch` recorded instead of re-guessing it; before this, only prose read it.

## [mcp-starter-v0.1.1] — 2026-10-21

### Fixed

- **`mcp-starter`'s example server crashed on startup, because its `mcp` dependency had no upper bound.** Both MCP plugins declared `mcp>=1.2.0`. `mcp` 2.x renamed `FastMCP` to `MCPServer`, so `from mcp.server.fastmcp import FastMCP` now raises `ModuleNotFoundError` at import. `mcp-starter` ships no `uv.lock`, so a fresh install resolved 2.x and the server never connected. `sqlite-readonly` kept working only because its lock holds `mcp` 1.28.1, and it would break the same way the next time the lock is regenerated. Both now declare `mcp>=1.2.0,<2`. In the lock, only the `requires-dist` line changed, so the resolved versions are unchanged. Verified by sending an MCP `initialize` request to each server: before the pin, `mcp-starter` failed on mcp 2.x with the error above; after it, `mcp-starter` (resolving mcp 1.30.0) and `sqlite-readonly` (1.28.1) both answered. Moving to 2.x is a separate migration, not part of this fix.

- **`live-eval` could outlive GitHub's job limit, and the thing it tests could change without a diff.** Two hygiene defects in the same job, both of which only bite once the suite is actually switched on — which is the reason to fix them while it is off. **No `timeout-minutes`:** 32 scenarios x k=3 run strictly sequentially at `runner.py`'s 240 s per-run timeout, a **6.4 h** worst case against GitHub's **6 h hard job limit**. Past it the platform kills the job, which reports `cancelled` and uploads no artifact — so the run produces neither the pass nor the fail it was asked for, *and* nothing to read afterwards. Now capped at **180 min**, a ceiling rather than an expectation (measured runs sit nearer 70–145 min); a cap that does not bite before the platform does is decorative, which a test asserts directly. **An unpinned CLI:** `npm install -g @anthropic-ai/claude-code` carried no version, in the one job whose *subject* is that CLI's behaviour — so a scenario could start failing because the tool moved overnight, and a failure with two candidate causes (the skill, or the CLI) cannot be attributed. That is the argument `evals/README.md` already makes for refusing to proxy the suite at another model, applied to the version rather than the vendor. Pinned to `@2.1.278`; bump it deliberately, as its own commit, so a behavioural change has a diff to blame. The `uv` install alongside it is gone — nothing under `evals/` shells out to anything but `claude` and `git`, so it was pure install time. +2 tests, both watched failing first: red against the pre-change workflow, and red again under mutation (`timeout-minutes: 400`, and the pin reverted to floating).

- **`live-eval` had failed every scheduled run since it was enabled, and the red was the feature working.** The weekly cron went in with `e8bd821`; the `ANTHROPIC_API_KEY` secret it requires was never added. So the job exited 2 on **6 of 6** scheduled runs between 2026-08-17 and 2026-09-21 and has **never once passed** — while every `push` and `pull_request` run stayed green, which is why it read as an intermittent CI fault rather than a permanent one. The `exit 2` is not the bug and has not been touched: "not configured" must not look like "passing", and the tempting fix — exit 0, paint it green — is the one thing this repo refuses everywhere else. The bug is that **"off" was being reported as "failing"**, and an alarm that has only ever been red is one people learn to skim past, after which its true alarms are skimmed past too (the same cost recorded two entries below for `bash_not_matching`). Three states now encode distinctly: flag off → **skipped**, flag on with no key → **fails, exit 2**, flag on with a key → the suite's own verdict. The gate is the repo variable `LIVE_EVAL_ENABLED` and not a test of the secret, because GitHub does not expose the `secrets` context to a job-level `if:` — only `github`, `needs`, `vars` and `inputs` — so key presence cannot be tested there at all. Default is off: an unset variable is the empty string, which fails `== 'true'`. `evals/README.md` gains the go-live checklist, because the flag is not paperwork — the suite's last full run was **28/32** with 24 scenarios gated on `pass^k` (72 runs must all pass, so ~2.5% chance of green at a 5% per-run flake rate), and no `timeout-minutes` against a 6.4 h worst case and GitHub's 6 h hard limit. Enabling it today would buy a slower, costlier red. Five tests pin all of it, each watched failing first: two went red against the pre-change workflow, and `test_missing_key_still_fails_loudly` was verified by mutating `exit 2` → `exit 0`.

- **The weekly cron fired at the top of the hour, which GitHub documents as the worst slot.** `0 6 * * 1` → `17 6 * * 1`. GitHub names `:00` a high-load window for the `schedule` event and advises another minute; under sufficient load a queued run is not merely delayed but **dropped**, leaving no run record at all — so a missing weekly check looks exactly like one that has not fired yet. Not theoretical here: the first two runs fired ~35 minutes late, the next four **5–6 hours** late. Pinned by `test_weekly_cron_avoids_the_top_of_the_hour`, which asserts the minute field of every cron in the workflow is not `0`.
